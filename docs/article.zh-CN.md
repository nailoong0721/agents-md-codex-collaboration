# 我的 AGENTS.md 配置：让 Codex 按明确的规则协作

> 分享我在 Codex 中使用的个人配置：怎样推进任务、复用授权、处理 Skill 冲突、验证结果，以及在 Windows 环境中可靠执行命令。本文同时介绍配置的安装、验证和迁移方法。

使用 Codex 时，有些要求会反复出现：执行任务要跟进到交付，已经确认的事情不必重复询问，检查要与改动的风险相匹配，结果说明要让人看得懂。这些长期要求适合集中写进 `AGENTS.md`，让后续任务有一致的协作基础。

我的这份配置分为两个部分：前五节约定协作方式，最后一节记录个人 Windows 环境的执行规范。下面先解释各部分的用途，再说明怎样把它们用到自己的环境中。

本文以 **2026 年 10 月 3 日**的个人配置快照为准。它是一份可供参考的工作约定；具体条款需要结合自己的习惯、项目和工具环境取舍。

## AGENTS.md 是什么

`AGENTS.md` 是供 Codex 读取的 Markdown 指令文件，适合保存相对稳定的要求，例如项目约定、交付标准、沟通偏好和工具使用限制。按照 OpenAI 的[官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)，Codex 会读取全局与项目范围的指令，并按规定的顺序组合它们。

在我的配置中，不同类型的信息各有位置：

| 位置 | 适合保存的内容 | 例子 |
| --- | --- | --- |
| 个人全局 `AGENTS.md` | 跨项目适用的协作方式和个人环境约定 | 如何确认授权、怎样报告验证结果 |
| 项目中的 `AGENTS.md` | 当前项目的开发和交付要求 | 测试命令、目录边界、验收标准 |
| Skill | 特定任务的工作流程及配套资源 | 制作文档、分析电路、整理研究资料 |
| 参考文档或操作手册 | 按条件查阅的详细说明 | PowerShell 复杂命令的处理方法 |
| 当前对话 | 本次任务的目标、范围和例外 | “这次只做分析”“只修改这个模块” |

这样的分工有助于保持主配置清楚，也让详细资料能在需要时再被读取。`AGENTS.md` 提供行为指导，实际执行仍受更高优先级指令、工具能力和权限设置约束；写入一个工具名称或路径，也不会自动安装工具。

## 我的配置包含哪些规则

### 1. 主动推进，同时明确完成条件

对应原文：`Initiative and Follow-through`。

这一节首先要求区分咨询和行动请求。咨询需要分析与建议；执行请求需要在授权范围内落实工作，并完成必要验证。

例如，“帮我比较这两种方案”需要有依据的比较；“按照第二种方案修改，并检查结果”则需要实际修改和检查。常规实现细节可以自主决定，与当前任务无关的改进应留在范围之外。

推进任务也需要停止条件：以用户要求的结果和项目验收要求为准，满足后结束。如果确实遇到阻碍，要说明已经完成什么、还缺什么，以及具体卡在哪里。

当缺少的信息会实质影响正确性、范围或授权时，应尽早澄清；与此同时，可以继续处理不依赖答案的部分。低风险的小歧义则可以说明合理假设后推进。

### 2. 复用已有授权，让必要的确认有具体内容

对应原文：`Authorization and Confirmation`。

这一节要求保留对话中已经建立的授权。对于同一项工作，只要范围和后果没有实质变化，就不应一再询问是否继续；如果范围或后果发生实质变化，或者更高优先级规则要求重新确认，就需要重新判断。

需要用户确认时，应先完成授权内的准备，给出可检查的结果。例如，用户只授权准备发布内容，就先完成稿件、检查和预览，再就发布本身请求确认。准备工作的授权不能自动延伸为发布授权。

因此，日常进度适合用陈述表达：“内容已经整理好，正在检查链接。”需要用户做决定时，才提出针对性问题。

### 3. Skill 影响任务时，说明具体依据

对应原文：`Skill Conflicts and Transparency`。

Skill 会为某类任务提供流程，但其中的条款有各自的适用范围。我的配置要求先判断条款是否适用，并区分明确要求、一般建议和模型自己的解释。

如果某个 Skill 导致暂停、额外确认、未完成请求或改变任务方向，需要指出实际读取的 `SKILL.md`，给出链接，引用相关原文，并解释它为什么影响当前任务。

用户的明确指令优先于一般 Skill 指导，同时仍需遵守更高优先级指令和实际权限限制。这让使用者能看清一次停顿或偏离来自哪里，也便于修正过宽或不合适的流程。

### 4. 验证与改动相匹配

对应原文：`Proportionate Verification`。

我的配置要求完成项目规定的检查，以及验证本次行为和实际风险所需的检查。之后是否增加测试，要有具体原因：新的修改、已出现的失败，或者尚未解决的疑点。

例如，只修改文章中的链接，通常应检查目标地址和渲染结果；修改数据转换逻辑，则可能需要验证边界输入和输出是否符合预期。如果项目另有强制检查，也应完成。

交付时要区分“实际验证过”“尚未验证”和“因条件限制无法验证”。这种表达比笼统地说“已经测试，没有问题”更有用，也能避免把结论扩大到证据之外。

### 5. 先交代结果，再提供必要证据

对应原文：`Communication Style`。

这一节约定输出顺序和表达方式：先说明主要结果，再提供理解结论所需的证据、原因和限制；根据问题复杂度决定篇幅。

列表、表格和标题用于帮助阅读。技术细节应帮助读者判断结果，而日常进度不必堆满内部操作过程。

### 6. 把 Windows 执行环境写清楚

对应原文：`Windows PowerShell 5.1 Core Policy`。

这一部分与我的电脑环境有关，内容比协作规则更具体。它默认按 Windows PowerShell 5.1 编写和执行命令；只有明确调用并核实 PowerShell 7 时，才使用相应能力。机器上存在 `pwsh`，不能据此推断当前命令已经运行在 PowerShell 7 中。

主要约定包括：

| 方面 | 配置要求 | 目的 |
| --- | --- | --- |
| 执行前检查 | 先判断路径、编码、原生进程、结构化数据、权限和链接等风险 | 在执行前选择适当写法 |
| 路径处理 | 对用户提供或生成的路径使用 `-LiteralPath`；.NET 文件操作使用绝对路径 | 避免特殊字符被当作通配符，或相对路径指向错误位置 |
| 编码 | 明确使用 UTF-8 读写；含非 ASCII 字符的 PowerShell 5.1 脚本使用 UTF-8 BOM | 减少中文乱码和脚本解析问题 |
| 运行环境 | 核实当前使用的解释器、工具入口和包 | 避免多个运行时之间混用依赖 |
| 子进程与数据 | 明确处理参数、Unicode 输入、JSON 序列化和退出码 | 避免命令看似执行，实际参数或数据已经变化 |
| 删除、移动和链接 | 核实操作范围，并处理 junction 等重解析点 | 防止目录操作越过预期边界 |
| 权限与排障 | 受保护位置和 UAC 操作需要明确授权；区分工具包装器失败和工具缺失 | 避免误操作或根据不足的证据重复安装工具 |

其中，一个容易混淆的细节是：普通 UTF-8 文本文件和 PowerShell 5.1 脚本文件的编码要求不同。我的规则使用显式编码写入普通文本；对于包含中文等非 ASCII 字符的 PowerShell 5.1 脚本，则要求 UTF-8 BOM。

我的环境还设有一层个人工作区依赖：首次依赖它处理相关任务时先运行 smoke test，要求退出码为 `0` 且 `FAIL=0`；每个需要该环境的新 PowerShell 进程都执行激活脚本。可选工具显示 `MISSING` 不代表核心检查失败，但当前任务如果需要它，仍要核实是否可用。

有些文档或媒体插件另有内置运行时。个人依赖层和插件运行时可以并存，需要验证的是本次实际使用的解释器和包。复杂排障步骤则保存在单独的 PowerShell 操作手册中，按配置列出的条件查阅。

### 第一步：选择全局或项目位置

希望个人协作习惯适用于多个项目，可以放入 Codex 主目录下的 `AGENTS.md`。默认位置为：

| 环境 | 默认位置 |
| --- | --- |
| Windows 原生环境 | `C:\Users\<用户名>\.codex\AGENTS.md` |
| macOS / Linux | `~/.codex/AGENTS.md` |

如果设置了 `CODEX_HOME`，应以该目录为准。使用 WSL 或远程环境时，也要确认 Codex 实际运行在哪个环境中，使用那个环境对应的配置目录。

只对某个项目成立的要求，可以放入项目根目录的 `AGENTS.md`。更具体的目录可以再补充自己的指令。例如：

```text
my-project/
├── AGENTS.md
├── frontend/
│   └── AGENTS.md
└── scripts/
    └── AGENTS.md
```

项目文件适合记录真实的测试命令、目录约定和验收要求。个人电脑的固定软件路径，则应留在个人环境配置中。

### 第二步：理解文件如何叠加

根据官方文档，Codex 启动一次运行时会建立指令链：先检查全局配置，再从项目根目录沿路径检查到当前工作目录。如果找不到项目根目录，项目范围只检查当前目录。

全局目录优先采用非空的 `AGENTS.override.md`，否则采用 `AGENTS.md`。在项目路径上的每个目录中，先检查 `AGENTS.override.md`，再检查 `AGENTS.md`，然后才是配置中指定的备用文件名；每个目录最多采用一个文件，空文件会被跳过。同一位置有效的 override 会优先于普通文件；不同层级的指令会组合，靠近当前工作目录的内容可覆盖更早的冲突指导。

这意味着，排查规则未生效时，要同时检查全局目录、项目路径和 override 文件。子目录规则的加载与运行时的当前目录有关，不应假设启动时会递归读取所有子目录的 `AGENTS.md`。

### 第三步：迁移本机约束

通用基础版可以作为起点。使用完整快照时，应先逐项核对环境相关内容：

| 原配置中的内容 | 迁移方法 |
| --- | --- |
| `C:\Users\SYSU\...` | 替换为实际路径，并核实对应文件存在 |
| `Windows PowerShell 5.1` | 按实际 shell 调整；macOS、Linux 用户可移除整段 Windows 规则 |
| `windows-powershell-5.1-safety.md` | 准备并维护自己的操作手册，或移除对不存在文件的强制引用 |
| `Test-CodexWorkspace.ps1` | 对接自己确实存在的环境检查流程 |
| `Activate-CodexWorkspace.ps1` | 对接自己的环境激活方式 |
| `Assert-CodexRecursiveTarget.ps1` | 准备对应的路径保护实现，或换成经过验证的操作约定 |
| `manifest.json` 与工作区依赖目录 | 按自己的工具管理方式调整 |
| `D:\Kicad\bin\kicad-cli.exe` | 使用 KiCad 时填写实际入口；不使用时删除该条 |
| 插件的 `load_workspace_dependencies` 工具 | 仅在当前环境确实提供该能力时保留 |

**本次下载提供的是配置文本，未包含这些配套脚本、工具和操作手册。** 它们属于个人环境依赖，复制 `AGENTS.md` 不会获得相应实现。尚未建立这些依赖时，从通用基础版开始最方便。

### 第四步：检查配置是否生效

保存为 UTF-8 文本后，在目标项目中新启动一次 Codex 会话或运行；CLI / TUI 可退出后重新启动。这样可以让新运行重新读取指令链。

先做一次只读检查，例如输入：

> 请列出当前生效的 AGENTS.md 和 AGENTS.override.md 文件路径，并概括它们对任务推进、授权确认和结果验证的要求。先不要修改文件。

这一步可用于初步判断。再选择一个范围很小、结果容易检查的实际任务，观察它是否按要求交付，是否说明验证结果，以及是否把无关改动留在任务之外。模型对规则的概括不能单独证明它在所有任务中都会正确执行。

如果结果不符合预期，依次检查配置目录是否正确、`CODEX_HOME` 是否指向别处、是否存在 override、当前工作目录是否正确，以及文件是否非空。官方默认的指令总大小限制为 `32 KiB`，由 `project_doc_max_bytes` 控制；内容过长也可能影响加载。[加载和排查说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## 怎样维护自己的版本

每次新增规则时，我建议明确三个问题：它适用于什么情况，希望改变哪个决定，以及做到什么程度算完成。例如，“认真测试”比较模糊；“完成项目规定的检查，额外检查由改动风险和未解疑点决定，并报告实际验证结果”就更容易执行和核对。

长篇排障细节可以放进参考文档，在主配置中写清读取条件。更换系统、工具目录或依赖管理方式后，也应同步更新相应路径和约定。

如果一条规则反复导致不必要的停顿、重复检查或范围扩大，应检查它的触发条件和边界。保留能影响实际决策的要求，删除已经失效或重复的内容，让配置与当前工作方式一致。
